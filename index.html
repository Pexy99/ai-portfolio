4. Project 1 — Model Evaluation on Real Notices
Project 1 · Core Challenge

Evaluating Models on Real Notices and Improving Extraction Quality

gpt-4.1-nanoInitial choice based on lower cost
↓
Requirement extraction failedZero requirements from two real attachments
↓
gpt-4.1-miniExtracted 7 and 19 items from the same documents
↓
Decision criteria · examples · rule validationCorrected 3 location-condition errors

Problem

The initial low-cost model returned no requirements from two notices containing explicit eligibility conditions, requiring a model decision based on both extraction quality and cost.

Solution

Compared candidate models on identical documents and prioritized the impact of missed mandatory requirements over the incremental cost.

01Extraction Quality vs. Cost

Compared nano and mini across six real attachments. Although mini cost 4× more per input token, projected usage was only about $1–2 per month, so requirement coverage took priority.

02Decision Criteria and Positive/Negative Examples

Defined whether a notice actually restricted bidder location, added positive and negative examples, and revalidated outputs with regex and keyword rules.

Results

  • Condition items extracted from the same two notices: 0 → 7 and 0 → 19
  • Kept empty forms at zero extractions and corrected 3 of 8 location-condition errors

7. Project 2 — RAG Evidence Data Layer
Project 2 · Core Challenge

Designing an Evidence Corpus for Trustworthy RAG

Security EvidencePolicies · Playbooks · Cases · API guides
↓
Evidence CurationCurate retrieval-ready evidence units
↓
Normalize to a Shared RAG SchemaTag risk, principal, system, and action type
↓
Load a Validated CorpusTrack provenance · exclude secrets

Problem

Evidence Selection: The system needed to retrieve risk- and system-specific policy, procedure, and API evidence while preserving links to the original source.

Data Boundary: Raw credential values could enter the corpus and LLM context.

Approach

Encoded evidence scope and provenance as metadata rather than relying only on semantic similarity.

01Curate and Normalize Evidence

Curated evidence units and tagged their applicable risk, system, and action type before converting them to a shared schema.

02Validate Provenance and Sensitive Data

Stored evidence identifiers, provenance, and change history; blocked raw credentials and duplicates before ingestion.

Results

  • Implemented a data contract, DDL, ingestion pipeline, and 9 initial evidence chunks
  • Enabled metadata-filtered Vector Search and answer provenance tracking
  • Designed 7 security remediation evaluation scenarioswith expected supporting evidence

9. Project 3 — Organization-Scoped LLM Context
Project 3 · Core Challenge

Building LLM Context from Query- and Organization-Scoped Evidence

Query and Current ViewDashboard · Case · Package
↓
SQL Retrieval by Organization and Work KeyOrganization · Review case · Remediation group
↓
Normalize Retrieved DataConvert to a shared grounding format
↓
Construct LLM ContextReturn cited evidence IDs and source links

Problem

Operational data and analysis documents were distributed across multiple tables, requiring context to be assembled for the current query and organization only.

Approach

Used PostgreSQL as the source of truth for structured state and left semantic retrieval as an extension point for unstructured documents.

01Context-Scoped SQL and Organization Validation

Restricted SQL queries to the organization and review target implied by the user’s context, then revalidated organization scope before every LLM call.

02Normalize Distributed Evidence

Converted operational records and analysis documents into a shared grounding format and returned only evidence cited in the answer.

Results

  • Built 3 context levels for dashboard, review case, and package views
  • Blocked generation before the LLM call when evidence from another organization was detected
  • Returned only evidence actually cited in the answer, with identifiers and source links
